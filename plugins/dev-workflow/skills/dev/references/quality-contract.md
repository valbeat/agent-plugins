# 実行環境に依存しない品質・停止条件

## 始める前

依頼の完了条件、許可された書き込み範囲、既存 PR・担当・ローカル変更を確認する。
対象リポジトリの AGENTS.md と関連 SKILL.md を実パスで読む。
スキルが読めることと、そこに書かれたツールが使えることを分けて記録する。

必要な runtime、パッケージ管理ツール、依存、ブラウザ、認証の存在を確認する。
秘密値を出力しない。環境不足は blocked とし、コード不具合の修正ループに入れない。
モデルや起動方法を変えて、権限・承認・quota の停止を迂回しない。

## 実装と検証

既存の TDD とプロジェクト定義の検証を維持する。必要な各検査は次のいずれかで記録する。

| 状態 | 意味 |
|---|---|
| passed | 対象の HEAD で実行し、成功した証拠がある |
| failed | 実行した検査が失敗した |
| blocked | 必要な環境・権限・承認等が揃わない |
| not_run | まだ実行していない。理由と再開条件が必要 |

実行できなかった検証を成功に変換しない。セルフレビューと別文脈のレビューを区別する。
検証後に変更したら影響する検査を再実行する。古い HEAD の結果は新しい HEAD の成功根拠にしない。
同じ失敗の修正は既存の3回上限に従う。停止しても dirty 作業や未 push commit を捨てない。

## 成果記録

対象 task、完全な head SHA、検査名・状態・証拠、成果URL、停止理由、再開条件を記録する。
全体は succeeded / no_action / blocked / retryable_failed のいずれかとする。
成功は依頼範囲の確認が全て passed の場合だけ。対象なしは取得成功と空結果を確認した場合だけ。
PR 作成、CI成功、マージ、反映確認は別の段階として依頼の完了条件に対応づける。
保存後は読み戻して一致を確認し、次の実行が重複 PR・コメントを作らないよう既存成果を照合する。

スケジュール、並列数、1ターン制約、実行 adapter は呼び出し側の責務。
この共通条件を理由に executor の制約やリポジトリのゲートを外さない。
